## What repeated

**① A status field said "fine" about something that was not — three separate documents, three
different subsystems.** [[crossplane-cloud-resources-as-crds]] had a managed resource report
`SYNCED=True READY=True` for two minutes about a ConfigMap that had already been deleted — Crossplane
polls, it does not watch. [[talos-kubernetes-local-cluster]] had both nodes report `Ready` while
`kube-flannel` crash-looped and no pod could get an IP — a healthy kubelet says nothing about the pod
network. [[harbor-installer-on-podman-arm64]] had nine containers reach `running`, seven of them
`healthy`, and a portal answering `200`, while every authenticated API call returned `502` because
redis was segfaulting under emulation. Each document links to at least one of the others as "the same
lesson," but only pairwise — none names this as a rule to check for on the next thing built. The
common shape: **a liveness/sync/running signal answers "did the last check succeed," not "is this
correct right now,"** and the only check that catches it is one that asks the actual thing (the pod
network, the API, the resource) rather than the status field describing it.

**② The same PromQL trap, hit independently in two documents four hours apart.**
[[slo-error-budget-burn-rate]] found that `sum(rate(...))` over a selector matching nothing returns
**no series, not zero** — a healthy service recorded no SLI at all until `or vector(0)` was added.
[[grafana-correlate-three-signals]] hit the identical failure the same day, in a dashboard error-ratio
panel that reads "No data" exactly when nothing is wrong. Both documents cite each other for it, so
the link exists — but it is worth naming as a standing rule for any new PromQL ratio or recording rule
in this repo, not just a coincidence between two pages written on the same day.

**③ An empty, `200`-status success is indistinguishable from a refusal — same week, two systems.**
[[opensearch-mappings-and-templates]] found that a protected system index answers every query with
`count: 0` rather than a `403`, so "empty" and "not allowed" look identical until compared against
`_cat/indices`. [[nexus-repository-hosted-proxy-docker]] found the same shape one page later: an
unauthenticated caller gets `200` and an empty repository list rather than a `401`. Both documents
cross-reference the other, so the pattern is at least on record, but a provisioning or verification
script anywhere in this repo that treats "got a `200`" as "it worked" should be treated as suspect by
default now, not rediscovered a third time.

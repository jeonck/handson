## What the week left behind

Ten published documents, all dated 2026-08-07: six install guides, one runbook, one troubleshooting
guide, one reference, one daily note. Nothing new was written this week. What happened instead is
that six of them were executed for the first time — the on-prem chain from
[[onprem-3node-kubeadm-ubuntu]] through [[metallb-l2-onprem]], [[longhorn-storage-onprem]],
[[ingress-nginx-onprem]] and [[cert-manager-onprem]] — and every one of them changed as a result.

So this is a week with no new knowledge and a great deal of corrected knowledge. The repository's
`verified` count went from three to nine; the interesting part is not the count but what the runs
had to break in order to move it.

## What repeated

**① A check that passes on a broken cluster.** Four separate documents, four different technologies,
one shape of defect: a verification step whose success condition is satisfied by something other than
the property under test. None of these failed loudly. All of them returned an answer that looked
correct.

| Document | The check | What it actually confirmed |
|---|---|---|
| [[onprem-3node-kubeadm-ubuntu]] | "one `calico-node` per node" | that the pods exist. All three sat at `0/1` permanently while nodes reported `Ready` and pods routed normally |
| [[longhorn-storage-onprem]] | replicas on distinct nodes, PVC `Bound`, data readable | all true — of a volume that was `degraded` from birth and never repaired |
| [[metallb-l2-onprem]] | `curl` the assigned address from the LAN | the node's own kube-proxy DNAT. Returned `200` on a network where L2 announcement cannot function at all |
| [[ingress-nginx-onprem]] | grep the demo page for the client address | the backend pod's own IP — the same value on a correctly configured cluster and a misconfigured one |

The common mechanism is that each check reads a *proxy* for the property instead of the property:
pod presence instead of pod readiness, volume usability instead of volume redundancy, an HTTP status
instead of an ARP resolution, any address instead of the client's address. Every proxy was true when
the real property was false.

The inverse also appeared once, in [[cert-manager-onprem]]: `openssl x509 -noout -subject` prints an
empty line for a certificate issued through an Ingress annotation, because ingress-shim sets no
common name. A correct result that reads as a failure sends someone hunting for a problem that does
not exist. Same root cause, opposite sign.

**② Failures that present as one broken machine.** Two documents produced a symptom localised to a
single node when the cause was cluster-wide configuration. [[onprem-3node-kubeadm-ubuntu]]: with
5473/tcp closed, the two nodes hosting a Typha replica reached it over loopback and recovered, and
the third did not — so a missing firewall rule looked like a faulty worker. [[longhorn-storage-onprem]]:
`longhorn-manager` does not tolerate the control-plane taint, so "three machines" silently means two
disks. In both cases the instinct is to debug the odd node out, and in both cases the node is fine.

**③ Ports that nothing in the repository opens.** 179/tcp and 5473/tcp (Calico) and 7946/tcp+udp
(MetalLB speaker memberlist) were all required and all absent from every ports table here. The
kubeadm ports table was assembled from the upstream Kubernetes ports page, which does not carry
Calico's or MetalLB's ports — the gap is inherited, and it will recur for the next component with
its own control-plane traffic.

**④ Undeclared dependencies between documents.** [[longhorn-storage-onprem]] set
`defaultReplicaCount=3` on the assumption of three contributing nodes, while
[[onprem-3node-kubeadm-ubuntu]] recommends leaving the control-plane taint in place. Each document
is defensible alone; followed in sequence they produce permanently degraded volumes. Nothing in
either document names the coupling.

**⑤ No document has been verified on the hardware it targets.** The six on-prem procedures were run
on EC2 and on containers sharing a bridge; [[argocd-helm-ha-install]], [[k8s-node-drain-replace]]
and [[pod-crashloopbackoff]] carry EKS in `env`. That is honestly recorded in each `env` field, and
it means the whole repository's `verified` column currently describes substitutes. The four gaps
named in [[onprem-3node-kubeadm-ubuntu]] — swap, `product_uuid`, `ufw`, NIC behaviour — are the
concrete cost.

## Should become a procedure

[[pod-crashloopbackoff]] is the only document in `03-troubleshoot/`, and `02-runbook/` holds only
[[k8s-node-drain-replace]]. The recovery work its branches describe — reading events before logs,
`--previous` on a restarted container, checking the probe before the process — has no runbook. It is
diagnosis, so it may legitimately stay a troubleshooting document; what is missing is the routine
that would prevent reaching it, which nothing here covers.

More pressing: the verification runs this week produced a repeatable rig
(`terraform-aws-lab/lab20-onprem-k8s-verify`, and the kind configuration recorded in
[[metallb-l2-onprem]]) that exists only as prose inside install guides. Re-verifying a procedure is
now recurring work with no procedure of its own.
